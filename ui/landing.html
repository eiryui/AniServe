Your AniList database, served as a REST API.

AniServe reads the AniList records already stored in your PostgreSQL database and answers with JSON for search, filters, schedules and detail pages. It is read-only and never calls AniList, so there is no rate-limit surprise at request time.

Everything your frontend asks AniList for, served from your own tables

A small read-only service in front of PostgreSQL. Your frontend talks to it, and nothing else.

Drop-in metadata API

Routes and response shapes match the AniList endpoints used by Eiryui and the Miruro API, so you point API_BASE at this server and change no frontend code. Reads come straight from your database instead of a rate-limited public API, and the JSON is identical to what AniList Indexer serves.

Read-only by design

Every database session is opened read-only. AniServe cannot create, change or delete a single row, so it is safe to point at a replica or a read-only role.

Always as fresh as the database

Whatever the indexer stores is what you serve. Countdowns such as timeUntilAiring are recomputed on every response, never served stale.

Never calls AniList

No crawler, no GraphQL client, no API key and no rate-limit budget to manage. The only thing AniServe talks to is PostgreSQL.

Per-IP rate limit

Protect your own API with a fixed-window limit. Clients get a JSON 429 and standard headers.

Diagnostics on demand

Development mode adds catalog counts and the indexer's job timestamps to /health, and logs errors to a file.

PostgreSQL and JSONB

Each record is read whole from a JSONB column, with GIN indexes on genres and tags for fast filtering. A connection pool is shared by all requests, and a database that is down at startup is retried instead of leaving the API stuck on 503.

From your database to your frontend

Something else fills the tables. AniServe only reads them, and requests only ever touch PostgreSQL.

Pagination, adult content, limits and errors

The same few rules apply to every route.

  1. 1

    Collections are paginated

    Pass page and per_page. per_page is 1 to 50 and anything outside that returns 422. Every list returns page, perPage, total, hasNextPage and results. The exceptions are /anime/{id}/characters, /recommendations and /relations: leave per_page out and you get the whole list in one response.

  2. 2

    Clients are rate limited

    Each IP gets API_RATE_LIMIT_RPM requests per window (120 per 60 s by default). Responses carry X-RateLimit-* headers, and an over-limit client gets 429 with Retry-After.

  3. 3

    Errors are small JSON

    Failures return { "detail": "…" }. 404 means the id is not indexed (yet), 503 means there is no database connection, 400 is an unknown sort and 422 is a page or per_page out of range.

  4. 4

    Adult titles need isAdult=true

    Every data route accepts isAdult (all except /health), including /list. With isAdult=true adult titles are included alongside the rest. Omitted or false, they are hidden from lists and search, /info/{id} and /anime/{id}/… return 404 for them, and they are removed from relations and recommendations.

Before you start

        
    
          
  • Set DATABASE_URL to the PostgreSQL that AniList Indexer fills
    • 
          
  • An empty or half-filled database is fine: the API serves whatever is stored so far
    • 
          
  • Set API_RATE_LIMIT_TRUST_PROXY=true only behind a trusted reverse proxy
    • 
          
  • Do not expose APP_ENVIRONMENT=development publicly
    • 
        

        
Development mode adds catalog counts and job timestamps to /health and writes errors to logs/error.txt.
